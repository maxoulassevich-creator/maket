# ЗАДАЧА

Ты продолжаешь начатую работу над интерфейсом сайта гастромаркета **Foodbeer / «ФудБир»**. К сообщению приложены два архива — распакуй оба в одну папку поверх друг друга. Внутри проектная документация, исходные документы и рабочий HTML/CSS/JS-прототип.

**Сначала прочитай `docs/` целиком, потом пиши код.** Там уже разобраны исходные документы, извлечена дизайн-система из макета и посчитан объём работ. Не переоткрывай это заново — просто продолжай.

# ЧТО ЗА ПРОЕКТ

Сайт на WordPress + WooCommerce, четыре части:

1. Публичная информационная витрина — **у физлиц НЕТ корзины и оформления заказа**
2. Закрытый оптовый контур — кабинет, персональные цены, корзина, заказ, PDF-счёт на предоплату, **онлайн-оплаты нет**
3. Модуль публикаций на сайт и в Telegram
4. Интеграция с 1С:УНФ

**Твоя задача — только интерфейс.** Тему WordPress делать не нужно. Нужны обычные статичные HTML-страницы, общий CSS и общий JS, которые открываются двойным кликом без сервера и без интернета.

Правишь `_src/`, запускаешь `python3 build.py`, получаешь готовые самостоятельные страницы. Синтаксис шаблонов — четыре конструкции, описаны в шапке `build.py`:

- `{{> partial }}` — вставить партиал
- `{{> partial arg="значение" }}` — с подстановкой
- `{{ключ}}` — переменная
- `{{#ключ}}…{{/ключ}}` — блок выводится, только если значение непустое

## Самое важное: роль переключает разметку, а не стили

ТЗ 4.1 прямо запрещает прятать кнопки через CSS. Поэтому содержимое для чужой роли лежит внутри `<template>` — браузер такое содержимое **в DOM не помещает вообще**:

```html
<template data-role-only="wholesale">…корзина…</template>
<template data-role-only="guest applicant">…«Подробнее»…</template>
<div data-role-hide="wholesale">…блок «Оптовым покупателям»…</div>
```

`prototype.js` разворачивает подходящий роли блок, остальные удаляет. Открой инспектор под гостем — узла корзины и кнопок покупки там нет физически.

**Не заменяй это на `display:none` ни при каких обстоятельствах** — это провалит критерий готовности ТЗ 25.2.

# ЧТО ДЕЛАТЬ ДАЛЬШЕ — В ЭТОМ ПОРЯДКЕ

**3. Личный кабинет** — 8 страниц `/account/…`: обзор, профиль, мои условия, акции и промокоды, заказы, заказ подробно, счета, безопасность. Донора в Organi нет ни у одной.

**4. Остальная публичная витрина** — акции, карточка акции, новинки, подарочные наборы, поиск, журнал (3 страницы), о гастромаркете, второй этаж, контакты, юридические.

# ЖЁСТКИЕ ПРАВИЛА — НАРУШАТЬ НЕЛЬЗЯ

1. У публичного посетителя нигде нет корзины, мини-корзины, кнопки «Купить», бронирования и предзаказа. Этих элементов **нет в разметке**, а не спрятаны стилями.
2. Шапка обслуживает три роли: гость видит «Войти» и «Опт»; заявитель — статус заявки; подтверждённый оптовик — название организации, скидку и корзину с суммой.
3. **Цена всегда с единицей измерения** — «за 100 г», «за шт», «за бутылку». Разметка `.price` + `.price__value` + `.price__unit`. Весовой товар без единицы читается как штучный.
4. Блок «Коротко» — абзац 40–70 слов сразу под заголовком, почти на каждой странице. Начинается с полного названия предмета, а не с местоимения.
5. Незаполненные данные не показываются вообще — ни прочерком, ни заглушкой. Секция без данных скрывается целиком.
6. Цвет статуса никогда не единственный носитель смысла — рядом всегда подпись. Класс `.status` рисует точку и текст.
7. Числа в таблицах моноширинные, по правому краю — класс `.num` на `td`/`th`.
8. Онлайн-оплаты нет. Везде, где заканчивается оформление, стоит явное пояснение про счёт на предоплату.
9. **Придуманные данные прямо запрещены (ТЗ 7.5).** Не выдумывай цены, остатки, состав, страну, производителя, сроки годности, сроки акций и размеры скидок сверх того, что уже есть в прототипе. Реквизиты, адрес, телефон и юридические тексты оставляй как `[заполняется перед запуском]`.
10. Никаких новых цветов, кеглей и отступов — только переменные из `assets/design-system.css`.
11. Таблицы на телефоне: класс `.table--cards` плюс `data-label` на каждой ячейке, иначе строки не перестроятся в карточки.
12. Каждая секция получает аннотацию — `<script class="ann" type="application/json">` с полями `section`, `what`, `how`, `why`, `src`. Это и есть согласованная текстовая спецификация: она живёт внутри прототипа, а не отдельным файлом.

# РАСХОЖДЕНИЕ ПО АЛКОГОЛЮ — УЖЕ РАЗОБРАНО, НЕ ПЕРЕРЕШАЙ

«Структура» описывает алкогольную витрину как полностью информационную («кнопок покупки нет в разметке»), а ТЗ 21.1, 12.1 и 25.3 разрешают подтверждённому оптовику класть алкоголь в корзину и оформлять заказ. По правилу приоритета главнее ТЗ.

Реализовано **три** случая, смотри `prototype/alcohol.html`:

- гость и заявитель — информационное состояние, кнопок нет в DOM, цена справочно;
- оптовик + товар **с** признаком доступности оптового заказа — корзина доступна, плашка с другой формулировкой (самовывоз со склада, счёт на предоплату);
- оптовик + товар **без** такого признака — кнопки нет, плашка объясняет причину. ТЗ 10.3 и 21.1 разводят признак алкоголя и признак доступности оптового заказа — это разные вещи.

Формулировки обеих плашек помечены как требующие утверждения магазином (ТЗ 21.2).

# ПРОВЕРКА ПЕРЕД СДАЧЕЙ КАЖДОЙ СТРАНИЦЫ

Открой страницу в трёх ролях и на ширине 430 px, убедись:

- горизонтального скролла нет ни на одной ширине (ТЗ 23.2);
- у гостя и заявителя ноль кнопок покупки и нет узла `.mini-cart`;
- не осталось неразвёрнутых `<template data-role-only>`;
- у каждой цены есть `.price__unit`;
- числа в таблицах моноширинные и по правому краю;
- битых изображений нет;
- в консоли нет ошибок.
